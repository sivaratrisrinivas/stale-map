Stale Map: how old is the copy an agent reads?

Package registries record the exact second every release goes out. That makes them a free, exact change clock. I used it to measure how far behind Parallel's index is on {{n_parsed}} registry pages that coding agents read, and to score recrawl policies against it.

3 · Recrawl policy

Which pages to refetch first

A crawler has a fixed budget, so the question is ordering. I froze every feature at {{cutoff}} and scored each policy on which copies were stale about a day later (the held-out day). The outside-view policies don't know when the index last crawled a page. The other two do, which is exactly what the index owner knows and what acquired_at exposes. Nothing was fitted on the labels.

{{ranker}} {{rtable}}

The classic change-rate policy (Cho & Garcia-Molina's Poisson model) beats uniform only a little here, and popularity does worse than random: popular packages are not the ones that ship most often. Once crawl time is known, the change clock covers 90% of stale pages with {{need_cc}} of the budget, against {{need_ap}} for Poisson-with-crawl-age and {{need_rc}} for the best outside-view policy. The ceiling is {{need_or}}. At a 50% budget the change clock catches {{cc50}} vs {{ap50}} (bootstrap 95% CI of the difference: {{ci_ap}} points).

The same order holds on a hash-held-out third ({{hold_n}} pages: change clock {{hold_cc}}, Poisson + crawl age {{hold_ap}}) and within each registry (change clock: {{within_cc}}).

The clock is frozen a day early, so it misses what ships on the held-out day: {{day_only}} of the {{n_eval_stale}} stale pages only went stale after the cutoff. Everything else was knowable from public timestamps before the day began. For registry-style pages, recrawling is mostly a lookup, not a forecast.

4 · What an agent can do today

Ask for a maximum age on registry domains

The Extract API already has the knob. For pypi.org, npmjs.com, crates.io and release pages, pass a maximum age and turn off the silent fallback, so a failed live fetch returns an error instead of a days-old copy:

POST /v1/extract
{
  "urls": ["https://pypi.org/project/openai/"],
  "objective": "latest released version",
  "advanced_settings": {
    "fetch_policy": { "max_age_seconds": 3600, "disable_cache_fallback": true }
  }
}

From Parallel's docs (Advanced Extract Settings): max_age_seconds minimum is 600, and disable_cache_fallback defaults to false. I didn't test this path, because this study used only the free, no-key MCP. On the free MCP, the cheap guard is to read acquired_at and, for a package page, check the registry's JSON (pypi.org/pypi/<name>/json, registry.npmjs.org/<name>). {{live}}

5 · Caveats

What this is not

  • A pilot: one snapshot, one morning, {{n_parsed}} pages. Not a verdict on Parallel's index, and Parallel may already track this internally.
  • A narrow slice of the web. Registry pages change on a known clock, so they are easy to measure, not typical.
  • Possible confound: PyPI sometimes serves bots a challenge, which could explain stale PyPI copies, since live fetch falls back to the cache. But with live fetch allowed, {{live_same}} of {{live_n}} responses on all four sites came back with the cached copy's acquired_at, so from the outside I can't say why.
  • The sample is popular pages that had shipped recently, so it over-weights fast movers. Copies of quiet pages are fresher by construction.
  • Crawl time is known to the day (acquired_at is a UTC date). The version bracket is exact, but only as tight as the gap between releases.
